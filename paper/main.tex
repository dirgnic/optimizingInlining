\chapter{Introduction}

The problem of choosing when to optimize during compilation remains difficult,
because compilers try to keep outputs predictable across platforms while also
minimizing code size. This has led to a preference for predetermined rules
called heuristics, which estimate when an optimization is useful. The issue with
normal heuristics is that they are not very adaptable, while choosing when to
optimize depends on multiple factors that can change together with the call graph
and with other compiler optimizations. This thesis studies inlining as one case
where this situational complexity matters: one choice can influence which
optimizations are possible next, the size of the code, and which other inlining
choices can follow
\cite{godbolt2019optimizations,theodoridis2022optimal}.

Inlining is one representative example of this compiler problem. By substituting
a call site with the instructions corresponding to the called function, several
simplification possibilities can appear: removing call overhead, enabling
devirtualization, propagating constants, removing dead code, and simplifying the
callee using information known in the caller. Although in many cases useful,
inlining can also lead to unnecessary code growth. To avoid this, production
compilers use thresholds and cost models that try to balance the cases where
code size increases too much with the cases where inlining reveals useful
optimization opportunities
\cite{godbolt2019optimizations,theodoridis2022optimal,mlgo}.

In the proposed method, the starting point is represented by several
deterministic heuristics called teacher policies. Models referred to as students
are trained on these teachers, with the purpose of testing whether they can learn
useful inlining rules from static call-site features. The pipeline keeps track
of the inline/no-inline choices of all teachers, evaluates them per module,
chooses the teacher whose rewrites give the smallest IR size, and uses that
teacher's choices as labels for training. The idea of using feature vectors
follows MLGO, while this prototype uses offline imitation learning instead of
MLGO-style online reinforcement learning
\cite{milepostgcc,mlgo,llvmmlgo,bcmax}.

The inlining of functions is a relevant case study, since it impacts both
call-level properties and general, global program behavior. The call-level
change is the choice to either substitute a call with the callee's contents or
to not edit the call site. The global effects appear through the changed
structure of the call graph, the size of the caller, the possible redundancy of
the callee, as well as new optimization options. This is reproduced in the
implementation at a smaller scale: a set of teachers is run on every module,
which results in inline/no-inline choices. In the case of the teacher per
module that gives the biggest reduction of the LLVM IR size metric, those
choices become labels for the training of binary classifier students.

For evaluation, LLVM IR is modified using LLVM's \texttt{opt} tool. The number
of LLVM IR instructions after rewriting becomes the main metric for
student-policy performance, while native object-file \texttt{.text} size is used
as a secondary reference metric.

\section{Compilation Pipeline}

The goal of compilation is to obtain a representation of code that can be
executed on a machine. The intermediate representation, LLVM IR, and its
corresponding instruction count are analyzed in this thesis because they are
affected by inlining choices while still being more general than machine code.
LLVM IR is generated before backend-dependent decisions, so it is useful for
studying optimization choices before the final target-specific code is emitted.
A simple version of an LLVM compilation pipeline is:

Clang is used for checking syntax and converting C/C++ files into LLVM IR form.
Following the optimization pass, the backend makes machine-dependent decisions,
such as allocating virtual registers in the IR to real registers and writing the
machine instructions that emit object files
\cite{cooper2011engineering,muchnick1997advanced}. LLVM IR is helpful for this
implementation because it is more abstract than machine code but still
lower-level than source code.

\section{LLVM and LLVM IR}

LLVM is a project for compiler infrastructure that includes optimization and
backend tools, as well as libraries. LLVM IR is just one part of the project,
corresponding to LLVM's implementation of an intermediate representation
\cite{llvmlangref,llvmpasses}. It has an abstract version of register allocation
called virtual registers, which get allocated at the backend stage, and also
operations per variable type, memory-level operations, branches, and calls.

\section{Static and Dynamic Measurements}

In the context of this thesis, two concepts are used: static and dynamic call
graphs, as well as static and dynamic code size. The static call graph contains
all possible call choices, regardless of inputs, while the dynamic call graph is
input-dependent and results from one execution of the code. Static code size
refers to the dimension of a generated intermediate or final compilation
representation, while dynamic code size is a measure of the executed
instructions
\cite{cooper2011engineering,godbolt2019optimizations}.

\chapter{Function Inlining}

Although inlining looks simplistic at a superficial level, when analyzing the
problem in depth, it can be seen that one inline choice, through integrating
the callee into the caller's context, can help further compact and optimize
code by using known values or context-specific simplifications. The original
call instruction may disappear, call overhead can be avoided, and later passes
can optimize values and control flow across the merged code region
\cite{cooper2011engineering,muchnick1997advanced,godbolt2019optimizations}.

\section{Cases Where Inlining Helps}

The examples given below were written for the purpose of this thesis. Small
auxiliary functions can be simplified easily when inlined:

\begin{figure}[H]
\centering
\begin{minipage}[t]{0.36\textwidth}
\begin{minted}[fontsize=\footnotesize,breaklines]{cpp}
int ab(int a, int b) {
    return a * b;
}
\end{minted}
\end{minipage}\hfill
\begin{minipage}[t]{0.55\textwidth}
\begin{minted}[fontsize=\footnotesize,breaklines]{cpp}
int sum_ab(int a, int b) {
    return a + b + ab(a, b);
}
\end{minted}
\end{minipage}
\caption{Small helper and caller before inlining.}
\label{fig:ab-sum-ab-example}
\end{figure}

Through inlining, the call to \texttt{ab} is substituted with the multiplication
returned by the function. This can improve the computation time needed for
changing the call context, called call overhead, if \texttt{sum\_ab} is executed
frequently, meaning it is in a hot path.

When the function call contains constants, inlining can eliminate unused cases,
sometimes by propagating constants. In the example below, inlining shows that
\texttt{c} is 0 and minimizes code size since the \texttt{c == 1} branch can be
eliminated:

\begin{figure}[H]
\centering
\begin{minipage}[t]{0.49\textwidth}
\begin{minted}[fontsize=\footnotesize,breaklines]{cpp}
// before:
string light_color(int c, int i) {
    if (c == 0)
        return light_red(i);
    if (c == 1)
        return light_green(i);
    return light_blue(i);
}

string car_color(int i) {
    int f = i;
    return light_color(0, 2 + f);
}
\end{minted}
\end{minipage}\hfill
\begin{minipage}[t]{0.47\textwidth}
\begin{minted}[fontsize=\footnotesize,breaklines]{cpp}
// after:
string car_color(int i) {
    int f = i;
    return light_red(2 + f);
}
\end{minted}
\end{minipage}
\caption{Constant-propagation example before and after inlining.}
\label{fig:inline-constant-example}
\end{figure}

\chapter{Problem Formulation}

Consider \(P\) a program or module, and let
\[
  C(P) = \{c_1,c_2,\ldots,c_n\}
\]
be the collection of call sites collected in the order of parsing the program
at inlining time. A call site represents places where functions are called in a
program, and for each call site \(c_i\), a feature vector \(x_i\) is extracted
during compilation, with data about the caller, the function which initiates the
call, and the callee, the function being called, as well as information about
the call graph:
\[
  x_i = \phi(c_i),
\]
where \(\phi\) is the function that gathers features. In the context of the
thesis, the features are static and composed of information about the caller and
callee, such as their structure, length, functions that call them, how many
constants they have, whether they are recursive, as well as some indices
regarding the call graph.

In inlining, \(A\) is the binary set of possible actions:
\[
  A = \{0,1\}, \qquad 0 = \text{do not inline}, \qquad 1 = \text{inline}.
\]

To give insight into how good an action might be, a policy is used that gives a
probability of action \(a\) for the vector of features \(x\):
\[
  \pi_\theta(a \mid x)
\]
where \(\pi_\theta(a \mid x)\) denotes the likelihood of choosing action \(a\),
given feature vector \(x\). Then, using \(\arg\max\), the inlining choice is
made:
\[
  d_\theta(x) = \arg\max_{a \in A}\pi_\theta(a \mid x).
\]

Inlining gives the problem a chronological and interdependent nature. By
applying policy \(\pi\) to program \(P\), the following trajectory is output:
\[
  \tau_{\pi}(P)
  =
  ((x_1,a_1),(x_2,a_2),\ldots,(x_T,a_T)),
\]
where \(T\) represents how many inline/no-inline choices should be made for
\(P\). As previously discussed, through the possibility of affecting later
optimizations, the decisions are dependent on each other \cite{mlgo,bcmax}.

In the presented prototype, the vector of features is static and collected at
the initial compilation stage from LLVM IR. This is done in an offline fashion,
because the information is not updated after every inlining choice or change of
the call graph, as an online inliner would do. The labels are predicted on this
raw data and then the call sites are changed in LLVM IR, without runtime
information.

The main scope is minimizing the size of the IR. In order to measure how well
policies perform in the implementation, the count of IR instructions after
rewriting is used:
\[
  \mathrm{Size}_{IR}(P,\pi), \qquad
  R(P,\pi) = -\mathrm{Size}_{IR}(P,\pi).
\]
The minus sign in the reward function is used because smaller values are
desired.

Let
\[
  \mathcal{H} = \{h_0,h_1,\ldots,h_k\}, \qquad
  h^\star(P_j)=
  \arg\min_{h_i \in \mathcal{H}} \mathrm{Size}_{IR}(P_j,h_i)
\]
be the set that includes all policies that act as teachers, and \(h^\star(P_j)\)
is the selected teacher for a module \(P_j\), which makes its IR size smallest.
Every teacher heuristic outputs an inline/no-inline choice starting from
information per call site.

The path taken by the best teacher gets included in the training set for the
students:
\[
  \mathcal{D}
  =
  \bigcup_j
  \{(x_{j,t}, a^{\star}_{j,t})\}_{t=1}^{T_j},
\]
where \(a^{\star}_{j,t}\) is the action that the chosen teacher policy
\(h^\star(P_j)\) decided on for the vector of features \(x_{j,t}\).

The new policy called a student should theoretically aim to predict labels as
closely as possible to its teachers, therefore minimizing a disagreement
function:
\[
  \min_{\theta}\sum_{(x,a)\in \mathcal{D}}
  \mathbf{1}[\pi_\theta(x) \neq a], \qquad
  \mathcal{L}(\theta)
  =
  -\sum_{(x,a)\in\mathcal{D}}\log \pi_\theta(a \mid x).
\]
The practical implementation uses a more direct approach: standard classifiers.
For probabilistic classifiers, this can also be written through binary
cross-entropy in order to obtain a probability.

The newly trained student can be used as a new policy and added to the teacher
set. It gives inline/no-inline predictions per feature vector corresponding to
a call site:
\[
  \hat{a} = \arg\max_{a\in\{0,1\}} \pi_\theta(a \mid x).
\]
What the trained model predicts leads to rewrites in LLVM IR, and the number of
instructions after rewriting is used as the performance metric.

\chapter{Related Work}

\section{Classical and Empirical Views of Inlining}

Before ML models, this difficult problem was tackled using classical inliners.
These attempted to find a compromise between code expansion and the chance for
future code simplifications when choosing whether or not to remove call sites.
Theodoridis, Grosser, and Su discuss how complex optimal inlining becomes when
weighing the impact on consecutive chains of function calls, code size, and
following optimization passes \cite{theodoridis2022optimal}. Godbolt gives a
similar interpretation for the use of inlining: it can merge code by using
known values, eliminate cases that are not needed, and simplify the callee with
information known in the caller \cite{godbolt2019optimizations,godbolt2025inlining}.

\section{Autotuning and Pre-MLGO Compiler Learning}

The idea of empirical search, as well as learning approaches, preceded MLGO.
MILEPOST GCC, for instance, constructs vectors of features in order to make the
optimization process more adaptive \cite{milepostgcc}. This was helpful in the
methodological sense for the thesis, since the concept of feature vectors was
reproduced, and it demonstrated that empirical data can be used for the training
of policies, even though its focus was general compiler optimization, not
inlining in particular.

The issue of having fixed predetermined parameters in inlining rules was
tackled by Cavazos and O'Boyle. They showed useful results by using empirically
adjustable parameters in place of static ones \cite{cavazos2005automatic}. The
problem they approached is similar to the one proposed here, but with another
scope, since they tried to tune policies automatically, while here the policy is
trained on other policies. The technical difference is therefore that autotuning
tries to find more appropriate parameters for heuristics, while behavior cloning
attempts to train a decision rule starting from feature vectors at call-site
level.

The focus on code size, specifically LLVM IR, is intentional in this thesis. It
is an easy-to-calculate and objective metric. Object size, also easy to
calculate, is listed secondarily. In order to assess real-world
performance, other metrics such as runtime have been attempted in the
literature, despite their difficulty to measure objectively and their dependence
on inputs and target platforms. In recent work, MLGOPerf uses ML techniques
modified toward minimizing both code size and performance metrics
\cite{mlgoperf}.

\section{MLGO}

MLGO was the initial inspiration for this thesis, because of the idea of using
trained models and their predictions for modifying LLVM IR with the purpose of
minimizing size \cite{mlgo,llvmmlgo}. The reinforcement-learning model in MLGO
uses states composed of call-graph indicators and call-site data, actions which
can be either inlining or not, and a reward showing how well the final compiled
program improved, usually through native code-size reduction. Using feature
vectors avoids the computational burden of capturing all characteristics of the
call graph. MLGO applies a policy-gradient technique, which is expensive because
each change needs to be recompiled and the reward can be calculated only at the
end \cite{mlgo}.

\section{Offline Imitation Learning and BC-Max}

Marinov, Agarwal, and Trofin show that computationally expensive online
reinforcement learning is not the only well-performing approach for this
problem. They propose using an offline model trained on predefined teachers
through imitation learning
\cite{bcmax}. For the scope of inlining, let:
\[
  \mathcal{H} = \{h_0, h_1, \ldots, h_n\}
\]
represent the collection of heuristic teachers, and let \(P_i\) be a module
with corresponding \(\mathrm{Size}_{IR}(P_i, h)\), meaning the size of the
rewritten IR with teacher \(h\).

The selected teacher per module has the smallest size of this rewritten IR:
\[
  h^\star_i = \arg\min_{h \in \mathcal{H}} \mathrm{Size}_{IR}(P_i, h).
\]
The trajectory corresponding to the selected heuristic's choices is the
following:
\[
  \tau_i = \{(s_1, h^\star_i(s_1)), \ldots, (s_m, h^\star_i(s_m))\}.
\]
Here, \(s_t\) corresponds to the feature vector for call site number \(t\).
Here, the learning is done in a supervised way, from the labels of the union of
the selected teachers, rather than by means of exploration and recompiling.

What teachers label individual call sites is context-dependent and sometimes
does not generalize. Two different teachers might assign different labels to
similar call sites in different modules, leading to disagreements in the set used
for training the behavior-cloning students. This is why the actual rewrite impact
is the real measure of success, not only how well the students agree with
teachers.

\chapter{Methodology}

The implementation follows Figure~\ref{fig:llvm-pipeline} until the output LLVM
IR step, whose size is the main objective to minimize. For every individual call
site, a feature vector is produced, the set of teachers is run to select the best
one per module, students are trained on those labels, and the labels predicted
by the student classifiers are reapplied to the IR using LLVM \texttt{opt}. How
sources are collected, how IR is generated, how teachers and students are
implemented, how IR is rewritten, and how IR size is determined remain visible
in the repository.

The dataset contains C/C++ files from various sources, including a small DCMTK
snapshot\footnote{DCMTK source repository:
\url{https://github.com/DCMTK/dcmtk}.}, 76 supplements from public sources
selected with inlining-relevance criteria, and synthetic sources generated
deterministically from a \(4^6 = 4096\) configuration space. For the generated
sources, the format, content, and size of callees and callers can vary, as well
as the order of calls and the arguments. This creates different function sizes,
branches, mathematical functions, recursion, constants, and variables. The 70
generated modules contain 1120 call sites, so teachers are run on both
representative inline and no-inline scenarios. Extending transferability beyond
this generated set remains future work.

Files from public sources are filtered using the criteria of successful
compilation to LLVM IR, the existence of a minimum of one local call site, and
the ability to pass the teacher-selection step and the corresponding IR rewriting
process. These steps happen at the data-collection stage, before training the
students. The features in the prototype represent local-level approximations of
the publicly available features used by MLGO: information about the call site,
the caller and callee, and the general program-level call graph, with flags for
recursive functions, constants, number of calls, and number of instructions.

\section{Teacher Heuristics}

In this thesis, a teacher heuristic means a deterministic policy used to produce
labels for student training. The local teacher set is intentionally simple and
inspectable. The teachers use deterministic rules starting from the same
call-site-level feature vector. Let \(s\) be callee size, \(u\) callee users,
\(b\) branch count, \(k\) constant arguments, and \(r\) a recursion flag. Most
rules use the following general shape:
\[
  \text{inline if } B(x)-C(x)>0,\quad
  B(x)\approx 2k+\mathbf{1}_{u=1}+\text{depth signal},\quad
  C(x)\approx s+b+\text{nested calls}+r .
\]
The exact thresholds are fixed in \texttt{teach.py}; the table gives the
readable form of each rule. The exception is \texttt{greedy\_ir\_size}, whose
labels are produced by measured rewrites in \texttt{rewrite.py}. Therefore,
most teachers are cheap proxy policies, while the greedy heuristic is slower
because it actually tests candidate rewrites.

\begin{table}[H]
\centering
{\footnotesize
\setlength{\tabcolsep}{3pt}
\begin{tabular}{|p{0.25\textwidth}|p{0.65\textwidth}|}
\hline
Teacher & Short rule \\
\hline
\texttt{never\_inline} & Conservative baseline: never inline. \\
\hline
\texttt{small\_callee} & Inline if \(s\) is small and \(r=0\). \\
\hline
\texttt{single\_caller} & Inline if \(u=1\) and the callee is not large; the
standalone helper may disappear after cleanup. \\
\hline
\texttt{constant\_argument} & Inline if \(k>0\), so caller-known constants may
remove branches or simplify expressions. \\
\hline
\texttt{cost\_budget}, \texttt{growth\_budget} & Inline if estimated growth
\(G\approx s\max(1,u)+b+\text{nested calls}\) stays under a budget. \\
\hline
\texttt{loop\_averse}, \texttt{hot\_leaf} & Prefer leaf-like callees; reject
large, branchy, or call-heavy callees. \\
\hline
\texttt{balanced\_score}, \texttt{llvm\_like\_size},
\texttt{benefit\_cost\_ratio} & Inline if \(B(x)/\max(1,C(x))\) passes a
threshold. \\
\hline
\texttt{aggressive\_speed} & Accept more small and medium calls, while still
rejecting recursive or clearly large cases. \\
\hline
\texttt{ml\_linear\_score} & Inline if \(w\cdot x+\beta>0\), using fixed
hand-written weights rather than training. \\
\hline
\texttt{bandit\_ucb\_proxy} & Inline if \(\widehat{g}(x)+\alpha/\sqrt{1+u}>0\):
estimated gain plus a small uncertainty bonus. \\
\hline
\texttt{rl\_value\_proxy} & Inline if immediate simplification plus future
call-graph value exceeds growth penalty. \\
\hline
\texttt{greedy\_ir\_size} & Measured teacher: order plausible non-recursive
candidates, try candidate rewrites, and keep a candidate only when the actual
rewritten IR instruction count decreases. \\
\hline
\end{tabular}%
}
\caption{Teacher policies as readable decision rules.}
\label{tab:teacher-policies-readable}
\end{table}

The ML-, bandit-, and RL-inspired teachers are approximations rather than
actually trained teachers. The measured greedy teacher is more expensive
because it orders plausible candidates from static features, then uses the same
clone-and-\texttt{alwaysinline} rewrite path as evaluation and keeps only
locally improving rewrites. This distinction matters because the student does
not learn from a single oracle; it learns from the teacher that behaves best
for each module under the rewritten-IR objective.

The main reported run uses one offline teacher-selection round: teachers are
evaluated, one teacher trajectory is selected per module, and students imitate
those selected labels. Chapter~8 also reports a small three-round check in
which the best learned student is fed back as another measured candidate
policy.

\section{Rewrite Algorithm}

The rewriting algorithm works at call-site level and applies an LLVM IR
transformation. For each selected call site, the callee is cloned, the selected
call is redirected to the clone, and LLVM performs inlining and cleanup.
Recursive or unresolved cases are skipped. This step is not the actual LLVM
inliner, but a smaller reproducible inlining mechanism built for the experiment.
During evaluation, inline predictions trigger this rewrite path, while no-inline
predictions leave the call site unchanged; the final metric is therefore
measured after predictions are materialized in LLVM IR.

The call-site order is deterministic and textual. Modules are analyzed in sorted
\texttt{.ll} filename order. Within each module, functions are visited in the
order in which their LLVM \texttt{define} blocks appear. Within each function,
call instructions are scanned from top to bottom. This is not dynamic execution
order and not a topological call-graph order. Non-greedy teachers and student
policies keep this extracted order when preparing rewrites. The measured
\texttt{greedy\_ir\_size} teacher is the exception: it first filters plausible
non-recursive candidates, orders them by benefit/cost score, and accepts a
candidate only when the actual rewritten IR instruction count decreases.

therefore depends on both parts of the setup: whether the teacher set contains
useful trajectories and whether the chosen model family can generalize those
trajectories to held-out modules. This is why several simple classifiers are
used rather than a single learner; each one represents a different compromise
between interpretability, flexibility, and risk of copying noise from the
selected labels.

\chapter{Evaluation}

In the evaluation stage, 163 C/C++ sources are compiled, resulting in 150 LLVM
modules with local call sites and 10394 call-site samples. The deterministic
module split uses 9009 samples from 124 modules for training and 1385 samples
from 26 modules for held-out testing. Teacher-label match measures agreement
with selected-teacher labels; the actual code-size effect is measured only
after predicted rewrites are applied.

In the teacher-evaluation and selection stage, every teacher is run on each
module in order to determine which one produces the smallest rewritten IR. On
held-out modules, this selected teacher is an oracle-style reference because it
is chosen after measuring all candidate teachers on those modules; it is not a
single deployable policy. Across all 150 modules, average rewritten IR falls
from 1985.39 instructions for never-inline to 1952.39 for this reference, a
1.66\% reduction. On the held-out split, the corresponding reduction is 1.10\%:

\chapter{Limitations}
\label{chap:limitations}

\begingroup
\small
\begin{itemize}
\setlength{\itemsep}{2pt}
  \item \textbf{Dataset scale.} One of the most important limitations is the
  scale of the dataset. In the main experiment, 163 C/C++ files were
  successfully compiled, and 10394 call-site samples were extracted, including
  examples from 76 public-source files. Even though this is enough for the
  implemented prototype, stronger generalization would require larger benchmark
  families, such as SPEC, cBench/MiBench, SQLite builds, and wider LLVM test-suite
  subsets.
  \item \textbf{Held-out scope.} The held-out split contains 1385 samples from
  26 unseen modules. However, all modules still come from the same general
  source collection and generator regime. A stronger future evaluation would
  use modules from more clearly different sources, in order to test whether the
  learned students generalize outside the current dataset composition.
  \item \textbf{Rewrite approximation.} In the main experiment, the feature
  vectors are extracted once from the initial LLVM IR. The chosen call sites are then
  rewritten by cloning selected callees, marking them with
  \texttt{alwaysinline}, and letting LLVM \texttt{opt} perform the actual
  inlining and cleanup. This is an offline approximation: the call graph and the
  feature vectors are not recomputed after every accepted decision, as they
  would be in a fuller online inlining system closer to LLVM's own inliner.
  \item \textbf{Metric scope.} The main scope of the prototype is minimizing
  rewritten LLVM IR instruction count. Native \texttt{.text} size and
  object-file size are used as secondary measurements, but final linked
  executable size and runtime behavior are outside the current evaluation.
  Therefore, the results should be interpreted as IR-level and artifact-level
  evidence, not as a complete performance evaluation.
  \item \textbf{Teacher and MLGO scope.} BC-Max-style selection can only choose
  among the available candidate policies. In this thesis, the teachers are
  deterministic and inspectable proxy heuristics, not production inliner
  policies. A full reproduction of MLGO would require deeper integration into
  LLVM, stronger learned or production-level teachers, and a much larger corpus.
  \item \textbf{Iterative scope.} A three-round BC-Max-style check was also
  attempted, where the best learned student was fed back into the set of
  measured candidate policies. This did not lead to larger improvements in the
  reported run. Moreover, this check does not include the uncertainty-based
  trajectory exploration used in larger BC-Max-style systems.
  \item \textbf{Generated-data filtering.} The generated modules are useful
  because they add diverse and controlled inlining cases, but they are still
  synthetic. A future generator could add a discriminator that rejects
  near-duplicate modules and keeps rarer or more informative inlining patterns
  before training.
\end{itemize}
\endgroup

\chapter{Conclusions}

\begingroup
\small
The purpose of this thesis was to study how compiler inlining can be optimized
using offline methods for learning policies, and to implement a reproducible
end-to-end pipeline that works with LLVM IR. In the reported run, 163 C/C++
sources are compiled successfully, 150 LLVM modules with local call sites are
evaluated, 16 teacher heuristics are run, 7 student models are trained, and the
predicted inline/no-inline decisions are applied back to LLVM IR through
call-site-level rewrites.

The main held-out result is measured on a source-level mix composed of DCMTK
files, generated modules, and 76 public C/C++ source files. On the 26 held-out
modules, the selected-teacher reference reduces the average rewritten LLVM IR
instruction count from 1569.23 to 1552.04, which corresponds to a 1.10\%
reduction relative to the never-inline teacher. For the student models, the
best held-out result by IR size is obtained by \texttt{deep\_forest}, which
reaches 1559.62 average IR instructions, corresponding to a 0.61\% reduction.
On the full artifact set, \texttt{conservative\_forest} reaches 1961.94 average
instructions and reduces rewritten IR by 1.18\%.

The comparison with LLVM \texttt{-Oz} shows that the prototype should not be
interpreted as a production-ready replacement for LLVM's full optimization
pipeline. On the standalone C/C++ files, LLVM \texttt{-Oz} reduces native
\texttt{.text} size by 14.91\% and object-file size by 28.76\% relative to
\texttt{no\_inline\_Oz}. The learned policies therefore demonstrate the
workflow and problem formulation, rather than outperforming LLVM's production
size pipeline.

The major contribution of the thesis is methodological. The implementation
connects source collection, LLVM IR generation, feature extraction, teacher
evaluation, behavior-cloning dataset construction, student training, rewrite
application, and artifact-level measurement in one reproducible workflow. The
results show that call-site-level inlining can be framed as an offline
policy-learning problem, where students imitate the best available teacher
trajectories and their predictions are then tested through actual LLVM IR
rewrites. Stronger future results would require integration with LLVM's real
inliner, larger real benchmark suites, stronger teacher policies, and
measurements on final linked binaries.
\endgroup
